# Architecture

이 문서는 프로젝트 사양의 각 섹션이 코드의 어디에 대응되는지, 그리고 스캐폴드가 강제하는 불변식(invariant)이 무엇인지 정리합니다.

## 1. 불변식

1. **IR이 유일한 원본.** `.kicad_sch`, `.kicad_pcb`, `.kicad_pro`, BOM, CPL, netlist, Gerber, 내장 3D 미리보기 `<project>.preview.glb`(`ArtifactKind.MODEL_3D`, PCB 단계가 보드 직후 컴파일 — 바이트 결정론적, 그림이라 판정을 기록하지 않음), kicad-cli의 STEP / GLB / 렌더(`<workdir>/3d/`, 거버처럼 KiCad 시각이 들어가 해시는 어떤 파일인지의 증거)는 전부 `ArtifactRef`로 등록되는 파생물이며 `generated_from_ir_hash`를 갖는다. `CircuitIR.content_hash()`는 **design view**(`model_dump(context={"view": "design"})`; 각 모델이 `drop_in_design_view`로 자기 필드를 뺀다 — 키 이름이 아니라 필드가 기준)만 해시한다: `validation`/`artifacts`(설계에 *대한* 상태), `project.workdir`/`project.created_at`(어디서·언제 만들었는가), `requirements.extraction_cache`(모델이 말한 것의 메모 — 2절 참조)·`requirements.presented`(사용자에게 보인 질문 텍스트의 sha256 — 대화의 bookkeeping; `confirm_design` 표는 라이브러리 경로를 담는다), 모든 `Provenance.created_at`(기본값이 현재 시각)과 `SourceRef`/`RegulatoryProvenance`의 `retrieved_at`(가져온 시각), 위치를 가리킬 뿐인 `SourceRef.document_path`·`LibraryRef.library_path`·`RegulatoryProvenance.source_document`(사본은 `content_hash`가, 라이브러리 항목은 verbatim 임베드와 ERC의 `lib_*_mismatch`가 고정한다), 그리고 규제 검증의 *결과*인 `RegulatoryRequirement.status`/`source_status`·`RegulatoryProvenance.verification_status`·`GroundedQuote.found`/`page`/`context`/`reason`(오프라인 실행과 온라인 실행이 다르게 채우는 것; 같은 이유로 `RegulatoryProvenance.section`·`applicability_rationale`은 규칙이 인용하는 절과 읽은 입력만 담고 페이지나 grounded 여부는 담지 않는다)를 제외한 **설계 내용만** — 같은 설계를 다른 폴더에서 다른 시각에 다른 KiCad 설치본으로 다시 만들거나 JSON에서 다시 읽어도 해시가 같다(`tests/test_spice_findings_regressions.py`, `tests/test_md_review_findings_regressions.py`). `SourceRef`·`RegulatoryProvenance`·`GroundedQuote`의 `content_hash`/`source_url`(어떤 문서를 썼는지)과 `GroundedQuote.quote`(어떤 주장인지)는 provenance이므로 해시에 남고 — 그래서 규제 문서의 *첫 성공 fetch*만이 해시를 움직이고 같은 사본을 다시 쓰는 실행은 움직이지 않는다 — 사용자가 `created_at`이라는 이름을 붙인 파라미터는 설계 내용이라 해시된다. `ArtifactRef.notes`(BOM 중화 내역 같은 컴파일 부기)도 design view 밖이다. IR이 저장된 뒤에 추가된 설계 필드(`PCBDesign.silkscreen`, `ManufacturingConstraints.min_silk_text_height_mm`/`min_silk_line_width_mm`, `Expectation.params`/`reference_vector`, `NetClass.rf_frequency_hz`, `SIConstraints.rf_length_fraction` — 이 넷은 `tests/data/ir_before_rf.json`(HEAD 0a2c4c7 코드가 저장·해시한 IR)이 증명 —, `CircuitIR.rf`, `Expectation.bound`, `PCBDesign.keepouts` — 이 셋은 `tests/data/ir_before_kr447.json`(42b0e53 코드가 저장·해시한 IR)이 증명)는 비어 있는 동안만 design view에서 빠진다(`drop_empty_in_design_view` — 모델이 자기 필드를 이름으로 지정, 키 이름 일괄 삭제 아님): 그 전에 저장한 IR은 해시가 그대로이고, 값이 생기면 다른 설계 내용처럼 해시된다(`tests/test_silkscreen.py`가 저장된 IR로 증명). `<workdir>/report.html`과 `<workdir>/pipeline.json`은 artifact가 아니다 — 검증 로그를 *기술하는* 파일이라 `ir.artifacts`에 등록되지도 해시되지도 않는다(§2 23행). `Traced` 값의 inf/NaN은 JSON이 담지 못하므로(`null`로 저장되어 다시 읽히지 않는다) 모델 경계에서 거부되고 `CircuitIR.load`는 비표준 `Infinity`/`NaN` 토큰을 `IRSchemaError`로 거부한다(`tests/test_md_review_findings_regressions.py` 60). 복사하거나 옮긴 프로젝트(기록된 절대 작업 폴더가 다른 폴더이거나, 작업 폴더 기록이 없거나 상대여도 등록된 산출물이 ir.json의 폴더 밖에 있는 IR — `workdir.stray_artifacts`)는 `run`/`review`/`report`/`stage-reports`가 거부하고, 그 작업 폴더를 다시 기록하는 `ai-eda relocate [--from OLD]`(`ai_eda/workdir.py`; 옛 폴더는 기록된 절대 경로, 아니면 산출물이 보여 주는 폴더 — 상대 기록과 끝이 같은 조상, 최상위 산출물의 폴더 — 아니면 `--from`; 알 수 없거나 재기록 뒤에도 폴더 밖에 남는 산출물이 있으면 exit 2, 아무것도 쓰지 않음)가 바꾸는 필드(`project.workdir`, `ir.artifacts`의 경로, `Evidence.path`, 위치 필드 `document_path`/`library_path`/`source_document`)는 모두 design view 밖이라 설계 해시를 움직이지 않으며(저장 전에 앞뒤 해시를 비교해 다르면 아무것도 쓰지 않는다), 프로젝트 잠금 파일 `<workdir>/.ai-eda.lock`도 artifact가 아니다 — 등록·해시되지 않고 GUI ZIP에도 들어가지 않으며 지워지지 않는다(`tests/test_workdir_relocate.py`).
2. **모든 중요한 값은 `Traced[T]`.** 값 + 단위 + `Provenance(kind, source, derived_from, inputs, tool, tool_version, note)`. `llm_generated`/`assumption`은 `needs_verification=True`. `derived` 값은 계산기가 직접 `inputs`(역할 → id)를 기록하므로 재계산은 위치가 아니라 역할로 호출을 재구성한다.
3. **검증 상태는 boolean이 아니다.** `worst_status([])`는 `NOT_VERIFIED`이다. 증거가 없으면 PASS가 아니다. `spice.rf.*`(RF 픽스처) 판정은 멤버 네트워크가 바인딩된 값 아래에서 어떤지일 뿐이다(회로도 수준: 트랙·접지 귀환 인덕턴스 없음) — 잘못된 네트워크는 요약이 FAIL, 잘못된 행은 그 행이 FAIL, 엔진·실행 환경이 없으면 NOT_VERIFIED.
4. **도구가 붙지 않은 ValidationResult는 의견이다.** `ValidationResult.tool`이 있어야 tool-backed. ERC/DRC 결과는 `tools/kicad/cli.py`만 생성하며 KiCad 버전·리포트 경로·검사 대상 파일 해시를 함께 기록한다.
5. **Agent는 설계 내용을 직접 수정하지 않는다.** `AgentResult.proposals: list[IRProposal]`를 돌려주고, `Orchestrator.apply_proposals()`가 설계 내용(design view에 드는 것)의 유일한 적용 지점이다(향후 GUI 확인/diff 훅). 페이로드는 대상 필드의 타입으로 검증된다(`topology`에 dict를 주면 `Topology`가 되거나 거부되고, `components`에 문자열을 주면 거부된다 — 오늘 해시되고 내일 로드되지 않는 IR은 만들어지지 않는다); `remove`는 설계 내용(`created_at` 제외)으로 대조하고 아무것도 지우지 못하면 오류다. artifact·validation 기록(`ir.artifacts`, `ir.validation`)은 설계가 아니므로 단계 러너·SPICE 단계(`SimulationAgent`, `run_spice_for`)·수리 전략이 직접 쓴다. 제안은 증거가 아니다: 검증 결과 없이 제안만 낸 단계는 `NOT_VERIFIED`("N proposal(s) applied, nothing verified")이지 PASS가 아니다.
6. **수리는 재생성 또는 재실행뿐.** `repair/strategies.py`의 `RegenerateArtifact`, `RerunTool`. `NON_REPAIRABLE` 카테고리(`human`, `regulatory_conflict`, `unverified_component_data`, `fab_capability_shortfall`, `circuit_structure_change`)는 `NotRepairableError`로 거부되고 `RepairOutcome.unresolved`에 사유와 함께 보고된다. `RepairLoop`는 모든 행위 전후로 IR 해시를 직접 재고, 해시가 바뀐 행위는 실패("changed the design")로 기록하고 루프를 중단한다(`stopped_reason = "repair strategy mutated the IR"`). oscillation 지문은 IR 해시 + 실패 검사 id와 그 수리 범주 + artifact 해시라서 재실행이 stale 리포트를 진짜 위반(`human`)으로 바꾼 것은 반복이 아니라 사람에게 넘길 진전이고, 실패한 행위는 루프가 진전한 다음 반복에서 다시 시도된다(재생성 뒤의 재실행); 행위가 하나라도 실패한 결과는 PASS가 아니라 `NOT_VERIFIED`다. 모든 시도(전략, 설명, 전후 해시, 오류, 시각)는 `RepairAgent`가 `repair.loop` ValidationResult의 `details.actions`로 IR에 남긴다(설계 해시 밖).
7. **외부 행위는 승인 필요.** `security.require_approval(ExternalAction, detail)` — 승인은 1회용·행위+세부내용 단위이며 일반화되지 않는다. 네트워크 fetch도 외부 행위다(`NETWORK_FETCH`, CLI `--online`이 "online session" 승인을 1회 grant+consume); 과금되는 모델 호출은 예산이 승인이고(`PAID_API_CALL`, `--llm-budget-usd`/`--llm-budget-tokens`), 사용자의 구독 로그인(Claude Code CLI)으로 모델을 부르는 것도 외부 행위다(`SUBSCRIPTION_USE`, CLI `--llm claude`가 `claude subscription via <cli 경로> (no per-call cost; usage shown)` 승인을 1회 grant+consume — 호출당 과금이 없으므로 예산은 per-call 제공자가 섞였을 때만 필수이고, 실행은 구독 호출의 토큰과 API 환산 추정치를 보여 준다); 승인 없이는 소켓이 열리지 않고(`tools/sources/archive.py`의 `fetch`는 요청을 만들기 전에 `ApprovalRequiredError`), 승인이 있어도 신뢰 origin(KiCad 라이브러리 Datasheet 호스트, 규제 후보 목록의 공식 도메인, 사용자가 준 호스트/정확한 URL — 포트는 origin의 일부라 443이 아닌 포트는 사용자가 준 정확한 URL로만)만, https만, URL당 실행당 1회만 fetch한다. 모델이 말한 URL은 호스트만으로는 절대 신뢰되지 않는다: 규제 제안(`ProposedRegulation`)의 URL은 그 호스트가 후보 목록의 공식 도메인 allow-list에 있고 사용자가 `accept_regulations`로 수락했을 때만, fetch 시점에 allow-list를 다시 확인한 뒤 fetch된다(IR에 저장된 `refused` 필드를 믿지 않는다). 127.0.0.1에만 bind하는 *listening* 소켓(`ai-eda serve`, `ai-eda gui`; `--host` 없음, Host 헤더가 이 기계가 아니면 421)은 바깥으로 연결하지 않으므로 외부 행위가 아니다; `gui`는 POST를 페이지 자신의 Origin과 `application/json`에만 허용하고(다른 출처의 페이지는 프로젝트를 만들거나 실행을 시작할 수 없다), 그가 시작하는 실행은 폼에서 `run_option_flags()`로 만든 플래그의 `ai-eda` 서브프로세스라 `--online`·예산·`--llm claude`의 승인은 그 서브프로세스의 게이트가 CLI에서와 똑같이 기록한다(GUI는 사용자가 채우지 않은 플래그를 더하지 않고, 키를 읽거나 보여 주지 않으며, 삭제·이름 바꾸기 엔드포인트가 없다 — 삭제는 `SYSTEM_DELETE`).
8. **KiCad 위반은 심각도와 무관하게 FAIL.** `tools/kicad/cli.py`는 error든 warning이든(사람이 exclusion 처리한 것 포함) 위반이 하나라도 있으면 `FAIL`을 낸다(`details.warning_policy`). warning을 PASS 뒤에 숨기면 `lib_symbol_mismatch`/`lib_footprint_mismatch` 같은 컴파일러 결함도 숨겨진다. 리포트의 컨테이너 키(`sheets[].violations`, `violations`, `unconnected_items`)가 없으면 "0 violations"가 아니라 `ToolExecutionError`다.
9. **레이아웃도 추적된다.** `Placement`/`Track`/`Via`/`Zone`은 `provenance`를 가진다(기본값은 `assumption` "origin not recorded"). `route_board`(`tools/routing/maze.py`)는 모든 트랙·비아에 `derived`/`routing.maze`(`derived_from`에 넷·배치·모든 파라미터)를, 픽스처용 `route_naive`는 `derived`/`routing.naive`를 스탬프한다. `grid_placement`(`PCBAgent`)는 `derived`/`placement.grid`를 스탬프한다(`derived_from`에 풋프린트·간격·여백·열 수; `inputs`는 비어 있다 — 계산기 역할 맵이 아니다). `core_ring_placement`(패드 32개 이상인 부품이 있을 때)는 `derived`/`placement.core_ring`을 스탬프한다(`derived_from`에 풋프린트·링·당김 각·그 출처·코어·간격·여백). `rf_floorplan_placement`(`ir.rf.blocks`가 있을 때)는 `derived`/`placement.rf_floorplan`을 스탬프한다(`derived_from`에 풋프린트·블록·영역·행·회전·간격·여백, 캔 안의 부품이면 `inside_can:<ref>,ring_mm:<링>`). keep-out이나 평면 넷을 받은 배선의 트랙·비아는 `routing.maze` 0.4로 스탬프되고 `derived_from`에 `keepouts:<ids>`/`plane_nets:<넷>=<층>;reach=3.0`이 들어가며, keep-out으로 잘린 평면 존은 `design.stackup` 도구를 유지하고 `derived_from`에 `pcb.keepouts[<id>]`를 더한다. `place_silkscreen`(`tools/silkscreen/place.py`)은 모든 `SilkText`에 `derived`/`silkscreen.place`를 스탬프한다(`derived_from`에 부품·패드·넷, 후보 번호와 이름, 문자 크기, 모든 파라미터; note에 금지 영역 규칙); `layout_items()`가 실크 문자도 나열한다. `review.ir_vs_pcb`는 검증이 필요한(unrecorded/assumption/llm_generated) 레이아웃 항목이 있으면 `NOT_VERIFIED`다. `Net.serves_requirements`로 패드→넷→요구사항 사슬이 이어진다.
10. **모델 출력은 제안이고, 사용자가 본 것만 확인할 수 있다.** LLM이 돌려준 것은 strict 스키마로 파싱된 뒤 결정론적으로 대조되어야 IR에 들어가고, 그때도 `llm_generated`다(`llm/extraction.py`). `user_requirement`가 되는 길은 (a) 사용자가 `--answer`로 직접 준 값, (b) 요청문 인용으로 grounding된 explicit 항목을 사용자가 **이전 실행에서 표로 본 뒤** `confirm_requirements`로 확인한 것, (c) 모델의 implicit/assumption 항목을 사용자가 `accept_implicit`로 개별 수락한 것뿐이다. 같은 규칙이 부품 후보(`confirm_parts`, 행 단위: 이전 표에 있던 행만)와 모델의 데이터시트 사실(`confirm_facts`: grounding은 인용·수량·단위 계열·주문표 행을 대조하지만 모델이 숫자에 붙인 *의미*는 대조하지 못하므로, 표를 본 사용자의 확인 전에는 IR에 아무것도 없다)에 적용되고, 모델이 아닌 결정론적 템플릿의 자유 선택값(`CircuitDesignAgent`: R2 = 10 kΩ, C = 100 nF, 허용차, ac 격자, LED의 이상 정전압 모델)에도 적용된다 — 첫 실행은 표와 필수 질문 `confirm_design`만 내고 설계 내용은 아무것도 적용하지 않으며(적용되는 제안은 아래에 말한 `requirements.presented` 기록뿐이다), 표를 본 사용자가 다음 실행에서 `confirm_design=yes`로 확인했을 때만 선택값이 `user_requirement`가 된다(`no`는 미적용; 같은 실행에 요구사항을 바꿀 수 있는 답 — 제어 키가 아닌 답, `confirm_requirements`/`accept_implicit`/`reject_implicit` — 이 있으면 무시하고 재질문; 표를 낸 실행은 표 텍스트의 sha256을 `requirements.presented`에 기록하고 확인은 그 해시가 이번 실행의 표와 같을 때만 유효하다). 결정되지 않은 `llm_generated` 요구사항은 `ir.llm_requirements`가 `USER_INPUT_REQUIRED`로 IR_BUILD를 막고, 리뷰어는 그것을 강제하지도(unserved FAIL 없음) 충족된 것으로 세지도 않는다(`NOT_VERIFIED`). 예산은 승인이며 **사전 조건**이다: 지출이 예산에 *도달*하면 다음 요청은 거부되고, 모든 요청에 `max_tokens`가 실린다(`llm/service.py`).
11. **부품 identity는 아카이브된 데이터시트가 만든다.** MPN이 authoritative로 *표시*된 것은 증거가 아니다. `parts/identity.py` `mpn_grounding`(IR_BUILD의 `ir.component_provenance`와 리뷰어의 `review.component_provenance`가 같은 함수를 쓴다)은 MPN의 provenance가 `authoritative`이고 그 `SourceRef`가 **아카이브 항목**(`<sha256>.meta.json`이 있는 디렉터리의 파일: 실행의 archive, `<workdir>/sources`, 또는 기록된 경로 자신의 디렉터리)을 가리키며(해시가 맞는 임의의 파일은 `unarchived` — 어디서 왔는지 아무것도 증명하지 않는다), 그 파일이 지금도 그 해시로 재해시되고, 현재 추출기의 텍스트가 meta에 기록된 텍스트 해시와 같고(아니면 `re-extracted`), 그 문서가 PDF이며(HTML 제품 페이지는 `not a datasheet`), **검사 시점에 MPN을 기록된 페이지에서 직접 다시 찾을 때만**(없으면 `not in text`; `page N`이 기록되지 않았으면 `no page recorded`) grounded로 본다 — 표시만 된 값은 `NOT_VERIFIED`(사유 기록), 변조된 파일은 `tampered`. `Component.mpn_tagged_authoritative`는 태그의 존재만 말하는 속성이지 grounding 검사가 아니다. MPN은 `component.existence.<ref>`가 아카이브된 PDF 본문에서 verbatim(대소문자·공백 무시, 온전한 식별자 — `LM2596S-5`는 `LM2596S-5.0/NOPB`에서 발견되지 않는다)으로 찾았을 때만 `ComponentAgent`가 authoritative로 재태깅한다(못 찾으면 `NOT_VERIFIED`, 절대 FAIL·추측 없음; note에 추출기·버전·텍스트 해시 스탬프). BOM의 `DatasheetHash` 열이 그 사본의 sha256을 싣는다.
12. **규제 단계는 출처와 적용 여부만 말한다.** `regulatory.compliance`는 항상 `NOT_VERIFIED`(엔지니어/인증기관이 판정)이고, `regulatory.sources`의 PASS는 정확히 "공식 문서를 아카이브했고 큐레이션 목록이 주장한 인용을 전부 그 본문에서 찾았다"이며, 인용을 못 찾으면 목록이 틀린 것이므로 FAIL이다. 적용 여부는 선언적 규칙 + 사용자의 범위 답변 + IR 요구사항으로 결정론적으로 판정되되 **`user_requirement`/`authoritative` provenance의 요구사항만 읽고**(모델 추출·가정·derived 값은 확인 또는 직접 답변을 요구하는 `USER_INPUT_REQUIRED`), 전압 규칙은 장비의 정격(`input_voltage`·`output_voltage` 요구사항 + 사용자의 `highest_rated_voltage`)으로 판정한다 — 하나라도 대역 안이면 적용, `NOT_APPLICABLE`은 전부 밖이고 최고 전압 답이 있을 때만; yes/no 질문에 yes/no가 아닌 답은 미결; 규칙이 다루지 않는 제외 조항은 항목의 `not_evaluated`로 rationale과 메시지에 실린다. 리뷰어 `review.regulatory_provenance`는 10개 provenance 필드·아카이브 항목인 해시 일치 파일·**모든 발견 인용의 리뷰 시점 재탐색**·결정된 적용 여부를 요구하며 모든 메시지에 "compliance not assessed"를 쓴다.
13. **신호 무결성은 필요한 곳에서만, 숫자는 계산기·grounding·확인된 선택에서만.** `ir.si`(넷 클래스·타이밍 경로)와 `ir.pcb.stackup`의 모든 수는 `Traced`이다 — 템플릿의 확인된 선택("a generic value, not a fab's"), 사용자 값, 데이터시트 사실(`t_rise`/`r_out`/`c_in`/`t_co`/`t_su`/`t_h` — 드라이버의 에지 값은 그 드라이버가 구동하는(출력·양방향 핀이 있는) 넷에서만), 등록된 계산기(`calc.tline.*`, `calc.ipc2221.width_for_current`, `calc.clock.divided`)의 `derived`. `--fab-capability`의 `stackup` 블록은 페이지에 grounding되고 보고되지만 이 버전에서는 `ir.pcb.stackup`에 기록되지 않는다(`mfg.capability_source`가 "not recorded in the IR"이라 말하고 PASS에 세지 않음). 선언되거나 임계 길이 규칙으로 승격된 넷만 제약을 받고, 어떤 넷에도 규칙이 없는 보드는 `routing.maze` 0.2와 바이트 동일하게 배선된다(보드 단위의 사실: 규칙이 하나라도 있으면 모든 넷이 한 협상에서 0.3으로 배선되어 규칙 없는 넷도 경로가 다를 수 있다). 임계 길이 규칙은 실제로 있는 선로 — 구리와 라이브러리 패드 상자로 뽑은 가장 긴 패드-패드 경로(`tools/si/paths.py`), 패드가 둘인 넷은 그 구리 — 를 재고, 가지를 모두 더한 구리(상한)는 '짧음' 방향으로만 쓴다(경로를 못 뽑으면 '길 수도 있음' = `NOT_VERIFIED`, 승격 없음). `spice.si`는 덱이 나타내는 회로(드라이버 하나·선로 하나·수신단 하나)인 넷만 판정하고, 패드가 셋 이상이거나 덱이 모델하지 않는 부품(R·C·L·스위치·크리스털 등)이 있거나 클래스 드라이버의 핀이 입력뿐인 넷은 이유를 적은 `NOT_VERIFIED`다. `si.*`는 IR 기하 + 계산기 검사이지 DRC가 아니고(메시지마다 그렇게 씀), `spice.si.<넷>`은 ngspice 도구 증거(덱·rawfile)다. 판정할 수 없으면 이유와 함께 `NOT_VERIFIED`: 적층 없음("no stackup"), 기준 평면 없음("impedance is undefined without a reference plane - use pcb_layers=4 or add a plane" — 숫자를 지어내지 않고, 지연은 상한 √εr/c0를 그 방향으로만 씀), grounding되지 않은 데이터시트 타이밍 항(키 이름). RF는 IR이 말할 때만 RF다: `NetKind.RF` 넷이나 `rf_frequency_hz`를 적은 넷 클래스의 넷(`tools/si/rf.py` `rf_nets`), 주파수는 그 클래스의 `rf_frequency_hz`, 없으면 확인된 `carrier_frequency` 요구사항뿐(모호하거나 미확인이면 주파수 없음). `si.rf_length`(RF 넷이 있을 때만)는 반송파판 임계 길이 규칙 l_crit = `rf_length_fraction`(확인된 선택, 기본값 없음; λ/10이 흔한 경험칙) × λ_g, λ_g = 1/(f·t_pd)를 임계 길이 규칙과 **같은 선로·같은 t_pd·같은 상한 표시**로 잰다 — 짧으면 PASS(평면 없는 상한으로도 유효), 평면 위에서 길면 클래스에 목표 Z0가 있을 때 `si.impedance`/`domain.rf.impedance`에 넘기는 NOT_APPLICABLE 행, 없으면 "needs impedance control" `NOT_VERIFIED`, 상한으로만 길면 "possibly long" `NOT_VERIFIED`; 승격·재배선은 하지 않는다. `domain.rf.impedance`는 RF를 가진 설계(RF 넷, `rf_frequency_hz` 클래스, 토폴로지의 RF 도메인)에만 선택되고 RF 넷을 가진 클래스별로 `si.impedance`의 행 중 **RF 넷의 행만으로** 판정한다(비RF 넷과 같은 클래스여도 그 넷의 PASS가 아무도 판정하지 않은 RF 구리를 대신하지 않고, 그 FAIL이 RF 판정이 되지도 않는다 — `other_members`로 맥락만 남고 `si.impedance.<클래스>`에 그대로 있다) — PASS는 RF 넷의 PASS 행을 통해서만, RF 행이 모두 `NOT_APPLICABLE`(모든 구간이 넥다운이거나 패드가 둘 미만)이면 RF 설계에서 '해당 없음'이 될 수 없으므로 사유를 붙인 `NOT_VERIFIED`이고 미배선 RF 넷도 `NOT_VERIFIED`이며, 정합 회로·S-파라미터·안테나는 판정하지 않는다고 명시한다. zone을 금지하는 keep-out(다각형은 bounding box) 아래 구리는 기준면이 없다(`tools/si/measure.py` `plane_keepout`/`KEEPOUT_NO_PLANE`): 그 `si.impedance`·`domain.rf.impedance` 행은 NOT_VERIFIED, 지연은 적층 전체의 최대 εr로 잡은 무평면 상한이며, `spice.si`·`si.critical_length`·`si.rf_length`는 "use pcb_layers=4 or add a plane" 대신 그 keep-out을 이름 댄다(`no_plane_reason`; 그 권고는 적층에 평면이 없는 층의 구리에만). RF 검사(`validation/rf.py` `RFChecksValidator`, 도구 `rf.checks`, `ir.rf`가 있을 때만 — 또는 자기 옛 결과를 대체할 때 —, SPICE 뒤 재실행)는 IR 산술·역할로 부르는 등록 계산기·이미 기록된 SPICE 판정(도구가 있고 현재 설계 해시인 것, 측정값을 읽을 때는 모든 증거 파일의 해시까지 일치)만으로 판정한다: `rf.regulatory_profile`(검증되지 않은 `kr447.*` 자리표시값)과 `rf.lab.<id>`는 PASS할 수 없고, 확인된 선택은 grounding이 아니므로 `rf.model_grounding`·`power.*`의 PASS는 출처 있는 authoritative 값에서만(`power.*`의 FAIL은 확인된 값끼리 모순일 때만), `rf.deviation`은 모든 인자가 이 설계에서 PASS일 때만 PASS/FAIL, 모델 값 위의 PASS는 'under confirmed model values'라고 쓰며, 더 이상 나오지 않는 자기 check id는 NOT_APPLICABLE로 대체된다. 뷰(보고서·GUI·그림)는 기록된 상태만 복사한다. 실제 임피던스는 fab의 측정만이 말한다.

Agent 단계의 상태 규칙 (`Orchestrator._agent_stage`): 필수 질문이 있으면 `USER_INPUT_REQUIRED`; `ValidationResult`가 있으면 그 최악값; 제안만 있거나 아무것도 없으면 `NOT_VERIFIED`(제안은 적용되지만 증거가 아니다). 파이프라인은 단계 상태가 `USER_INPUT_REQUIRED`이거나 **필수 질문이 하나라도 있으면** 멈춘다 — IR_BUILD에서 `ir.connectivity`의 FAIL이 `ir.assumptions`의 `USER_INPUT_REQUIRED`보다 상위로 집계되어도 사용자는 질문을 받는다(`tests/test_md_review_findings_regressions.py`). 단계가 만든 check id를 `consumes`로 읽는 검증기(`component.fit`·`domain.power.thermal`·`domain.analog.bias` ← `spice`)는 그 단계 직후 다시 실행되어 결과가 `ir.validation`에 추가된다(단계 상태는 agent의 판정 그대로, 메시지에 `re-validated: ...`로 표시). 세 검증기는 같은 신선도 사슬(`tools/spice/evidence.py` `fresh_spice_run`: 최신 tool-backed `spice` 결과 + 현재 IR의 디스크 일치 netlist + 그 해시를 이름하는 변경 없는 `results.json`)로만 op를 읽고, 파생 값(P, Tj)은 결과 details에만 두어 IR 해시를 바꾸지 않는다(테스트가 해시 불변과 `calc.recompute` PASS를 단언). PLACEMENT는 이 규칙의 예: `PCBAgent`는 `ValidationResult`를 내지 않으므로 배치했으면 "1 proposal(s) applied, nothing verified", 못 했으면 "not placed: 사유"로 언제나 `NOT_VERIFIED`다. FAB_CAPABILITY도 파일이 없고 IR에 authoritative 한계값이 없으면 메모만 남기고 `NOT_VERIFIED`다(질문 없음). `_manufacturing_outputs`는 gerber export의 `ToolUnavailableError`를 `worst_status(statuses + [NOT_VERIFIED])`로 집계하므로 앞선 BOM/CPL FAIL을 버리지 않으며, BOM이 셀을 중화했으면 단계 메시지에 `bom: N cell(s) neutralised (R1.Value, ...)`를 덧붙인다. SCHEMATIC 단계는 회로도 컴파일 성공 뒤 `<id>.kicad_pro`를 함께 컴파일한다(`compile.kicad_pro`; 회로도의 메시지가 단계 메시지로 남고 `; project file: <path>`가 덧붙는다).

REQUIREMENT_ANALYSIS 단계의 LLM 흐름과 **신뢰 모델** (`RequirementAgent`, `ctx.llm`이 `LLMService`일 때; 없으면 종전의 체크리스트 동작 그대로):

```
request_text = raw_input + "Correction from user: …"×N ──sha256──▶ extraction_cache 조회 (같은 텍스트 + 같은 fingerprint면 호출 없음)
   ├─(hit이지만 extraction_version/prompt_hash(보낸 프롬프트 전체)/schema_hash/quantity_version이 다르거나 저장된 응답이 스키마에 안 맞거나 model이 없음)─▶ miss로 취급(사유를 노트), 크래시 아님

              ──▶ 모델 출력을 verbatim으로 캐시(fingerprint·모델·usage·청구된 모든 attempt의 비용·presented=False·confirmed=False·decisions={})

   explicit + 토큰 경계의 verbatim 인용 + 요청 그 자리에서 재파싱한 값 = 모델 값 ──▶ Requirement(explicit/given, text="<key>: <인용>", value: llm_generated, tool=model, note="quote: …; parsed: …; model: …; model statement: …")
   explicit인데 인용 없음/조각/불일치   ──▶ Requirement(assumption/assumed, value: assumption, note="demoted from explicit: <사유>")  → ir.assumptions가 USER_INPUT_REQUIRED

   같은 key, 다른 종류                  ──▶ 값은 옮겨가지 않고 하위 항목은 req.<key>.<kind>로 분리(notes)
   지시문 구절 포함                    ──▶ drop (details.dropped에 사유)
   application(인용 필요)             ──▶ req.application (llm_generated)         jurisdictions(인용이 그 코드를 지칭해야) ──▶ Jurisdiction(provided_by_user=False) — `jurisdiction_known`에 안 셈
제안: requirements.requirements 교체(추출 유래 항목만 교체, 사용자가 직접 답한 항목은 유지·키 충돌 시 사용자 답 우선 — 나중 실행의 `--answer key=`도 추출·확인된 항목을 대체한다; 저장된 accept/reject 결정 재적용), requirements.conflicts, regulatory.jurisdictions, requirements.missing = (기본 질문 + 모델 질문(source="llm")) − 답해진 것 + **필수 질문 `confirm_requirements`**(추출 표: key/kind/value/category/**요청 문맥**/basis) → 캐시 항목 presented=True
결과: ValidationResult "requirements.extraction" (tool=요청한 모델, tool_version=`model_used`, details: counts/demoted/dropped/notes/cost(청구된 attempt 하나라도 미상이면 unknown)/cached/presented/confirmed/decisions/attempts) = USER_INPUT_REQUIRED
--answer confirm_requirements=yes|y|ok|confirm|네|예|확인… (구두점 무시; `네 맞습니다`처럼 확인 단어들만으로 된 답도) ──▶ 캐시 항목이 **이전 실행에서 presented**일 때만: upgrade_confirmed로 grounded explicit(+application)만 user_requirement(note="confirmed by user; quote: …; model: …"), Jurisdiction.provided_by_user=True, 질문 제거, 캐시 항목 confirmed=True, 결과 PASS   (이번 실행에서 (재)추출됐거나 아직 보여 주지 않은 항목이면 "confirmation ignored" + 다시 표; conflict가 남아 있으면 확인 거부)

IR_BUILD: ir.llm_requirements ──▶ 결정되지 않은 llm_generated 요구사항이 있으면 USER_INPUT_REQUIRED(키와 답 방법 명시); 리뷰어 review.requirements_vs_ir ──▶ 검증 필요(llm_generated/assumption) 요구사항은 unserved FAIL에서 제외하고 served로도 세지 않으며 NOT_VERIFIED로 이름을 댄다
```

즉 `user_requirement`가 되는 것은 (a) 사용자가 `--answer`로 직접 준 값, (b) 요청문 인용으로 grounding된 explicit 추출 항목을 사용자가 표로 본 뒤 `confirm_requirements`로 확인한 것, (c) 모델의 implicit/assumption 항목을 사용자가 `accept_implicit`로 개별 수락한 것뿐이다. 모델의 implicit 추론과 assumption, grounding에 실패한 주장은 확인해도 `llm_generated`/`assumption`으로 남는다(사용자는 자기가 *말한 것*을 확인한 것이지 모델의 추론을 확인한 것이 아니다). 대조되지 **않는** 것은 모델이 인용에 붙인 key와 category다 — `12V`를 `output_voltage`로 분류한 것은 그대로 12 V로 grounding되며, 확인 표의 "in your request" 열(인용 앞뒤 20자)이 사람이 그것을 잡는 유일한 곳이다. `extraction_cache`는 IR 파일에 저장되지만 `content_hash`에서 제외되고(모델이 말한 것은 설계가 아니다), `corrections`는 사용자의 말이므로 해시에 들어간다(`tests/test_requirement_agent_llm.py::test_extraction_cache_is_not_design_content_but_corrections_are`). CLI `run`은 파이프라인이 어디서 죽든 `finally`에서 IR을 저장하고 LLM 사용량을 출력하므로 유료 추출이 나중 단계의 결함에 사라지지 않는다.

SPICE 단계의 상태 규칙 (`SimulationAgent` + `tools/spice/stage.py`): `ir.simulation` 없음 / 엔진 없음 / 바인딩된 부품 없음(`NothingToCompileError`) → `NOT_VERIFIED`; 컴파일러가 거부(`CompileError`: 바인딩 없는 부품, `llm_generated` 값·컨테이너, 떠 있는 핀, `electrical`과 다른 SPICE 값 …) → `FAIL`(human); 분석이 실패(ngspice stderr, ControlledExit, 타임아웃 …) → `spice` `FAIL`(human, ngspice의 오류 줄 포함) — 단, *환경*이 막은 경우(`SpiceResult.unverifiable`: rawfile을 쓸 곳이 없음, 죽은 엔진, 코드 모델 미적재 + `A` 소자)는 `NOT_VERIFIED`(설계에 대한 판정이 아님); 기대값은 `|measured − nominal| ≤ max(tol_abs, tol_rel·|nominal|)`로 판정(허용치 없음, 또는 `nominal == 0`에 `tol_rel`만 → `UNRESOLVED`, 벡터 없음 → `FAIL` "vector not produced"; `reduce=frequency`는 `rising_edge_frequency`의 측정값을 판정하고 에지 수·첫/마지막 에지 시각·임계값·vmin/vmax를 `details.frequency`에 남기며, 셀 수 있는 상승 에지가 3개 미만이거나 스윙이 엔진 해상도 이내이면 "no oscillation detected" `FAIL`(human) — 결코 PASS가 아니다; `at`/`frequency`에서 플롯에 스케일 벡터가 없으면 "scale vector not produced"로 스케일 이름을 보고한다 — 기대값 벡터가 없다고 하지 않는다; 레벨·구간 축약 `db_at`/`rms`/`db_rms`/`harmonic_dbc`/`am_depth`는 창·최대 간격과 한계·진폭·기준 레벨·편차 한계를 `details.<축약 이름>`에, params와 `reference_vector`를 `details.params`/`details.reference_vector`에 남기고, 숫자를 낼 수 없으면(격자가 너무 성김, 기준 0, 기본파 없음, 창이 저장 구간 밖) 이유와 함께 `FAIL`(human), 엔진 해상도 이하의 고조파 레벨은 측정되어도 PASS가 되지 않는다(`NOT_VERIFIED`, `details.unresolved`); `db_at`은 두 크기를 같은 두 샘플 사이에서 읽어 dB bracket으로 `at`처럼 판정한다); `at`이 샘플 사이에 있으면 보간(dc/tran 선형, ac는 log-주파수·크기 벡터는 log-log)하되 두 이웃 샘플이 `details.bracket`에 기록되고 **두 이웃 모두 허용치 안일 때만 PASS**, 둘 다 같은 쪽으로 밖이면 FAIL, 그 사이면 `UNRESOLVED`("grid too coarse") — 보간 오차가 설계 편차로 보고되지 않는다; netlist가 `assumption` 값/결정 위에 서 있으면 PASS 대신 `NOT_VERIFIED`(FAIL은 FAIL); 요약 `spice`는 기대값 결과의 최악값(기대값이 없으면 `NOT_VERIFIED`); 모든 결과에 `conditions`(부품 값 nominal, 온도 `.temp` 또는 ngspice 기본 27 °C, 코너 미시뮬레이션)와 엔진 스탬프(빌드·코드 모델·설정 해시)가 붙는다; 설정에서 제거·개명된 기대값의 옛 `spice.<id>`는 `NOT_APPLICABLE`로 대체되어 RELEASE를 막지 않는다. 한쪽 한계 `Expectation.bound`(`at_least`/`at_most`)는 허용치를 대신한다: 측정값이 보간·bias 구간 전체로 nominal의 통과 쪽이면(같으면 통과) PASS, 전부 실패 쪽이면 FAIL, 걸치면 UNRESOLVED이고 `details["bound"]`·`tolerance=None`·부호 있는 편차가 남는다; 컴파일러는 한계 + 허용치, 한계 + `requirement_id`를 거부하고 한계는 dB 레벨의 `tol_abs` 규칙을 면제한다; `judge`는 `RFExpectation`도 같은 함수로 판정하며, `spice.rf.*`는 픽스처 러너의 결과라 SPICE 단계가 은퇴시키지 않는다(`RF_CHECK_PREFIX`; 러너가 자기 것을 대체).

컴파일 단계의 상태 규칙 (`Orchestrator._compile`, BOM/CPL·gerber/drill 포함): 판정은 tool-backed `compile.<kind>` ValidationResult로 `ir.validation`에 남는다(PASS는 쓴 artifact의 해시, FAIL은 `repair: human`) — RELEASE·`ai-eda run`의 종료 코드·`ai-eda review`가 그것을 읽는다; `NothingToCompileError`(부품 없음, `ir.pcb` 없음, 내보낼 PCB artifact 없음)·`NotImplementedError`(아직 없는 컴파일러) → `NOT_VERIFIED`; 그 외 `CompileError`(핀 불일치, 미검증 심볼/풋프린트, 넷에 없는 핀 …) → `FAIL` + 메시지; 다른 예외는 결함이므로 전파. 거부된 종류의 오래된 artifact는 증거로 남지 않도록 제거한다. 빈 회로도는 ERC를 "0 violations"로 통과하므로, 부품이 없는 IR은 회로도를 아예 쓰지 않는다.

## 4. 리뷰어가 FAIL을 내는 방식과 수리 매핑

| 리뷰 결과 `details` | 전략 |
|---|---|
| `{"repair": "regenerate", "artifact": <ArtifactKind>}` 또는 `"artifacts": [...]` | `RegenerateArtifact` → 등록된 컴파일러/exporter로 재생성 (한 행위로 여러 종류; `CompileError`·도구 부재는 실패한 행위로 보고) |
| `{"repair": "rerun_tool", "tool_check": "kicad.erc"\|"kicad.drc"\|"spice"\|"mfg.gerber"\|"mfg.drill"}` 또는 `"tool_checks": [...]` | `RerunTool` → kicad-cli 재실행 / `run_spice_for` 재실행(fresh한 netlist에만) / 출력 형식 검사 재실행 |
| `{"repair": "human"}` 등 `NON_REPAIRABLE`, 또는 `repair` 키 없음 | 거부, `unresolved`에 보고 |

리뷰어가 증거를 읽는 방식: `review.ir_vs_*`는 `ArtifactRef.is_stale`/`matches_disk`(다중 파일 artifact는 `files` 집합 해시), `review.ir_vs_pcb`는 추가로 레이아웃 항목의 provenance(불변식 9); `review.pcb_vs_bom` / `review.pcb_vs_cpl`은 (1) CSV의 reference/designator 집합이 IR과 같고 (2) CSV가 stale이 아니며 (3) 디스크 해시가 기록과 같고 (4) 보드 artifact가 있고 fresh·디스크 일치일 때 `tools/kicad/board.py`로 읽은 보드 풋프린트와 행 단위로 대조한다(BOM: reference·Value·Footprint id — Value는 `csv_cells.bom_cell_text`로 선행 `'` 하나를 벗긴 설계의 말과 보드 Value를 대조하고, 셀이 그 말과 다르면 불일치 메시지에 `(BOM cell ...)`로 셀도 이름한다, CPL: 위치 1e-4 mm·회전(정규화)·면) — (1)~(3) 위반은 `regenerate`(BOM/CPL), (4)의 stale 보드는 `regenerate`(PCB), 보드 없음은 `NOT_VERIFIED`, fresh한 둘이 불일치하면 컴파일러 결함이므로 `human`; 결과에는 CSV와 보드의 경로·디스크 해시가 `Evidence`로 붙는다. `review.schematic_vs_pcb`는 최신 `kicad.drc`가 (a) 현재 보드에서 실행되었고 (b) parity를 실제로 평가했으며 (c) 현재 회로도(`schematic_hash`)에 대해 평가했고 (d) parity 항목이 0개일 때만 PASS — parity 항목은 KiCad 심각도가 warning이어도 FAIL(`human`); `review.erc`/`review.drc`는 도구 결과를 그대로 통과시키되(tool이나 artifact 해시가 없는 결과는 의견이라 `NOT_VERIFIED`; `review.manufacturing_capabilities`·parity도 같다) FAIL이면 `human` + 위반 타입 목록 — `review.drc`는 `KICAD_PROJECT` artifact가 등록되어 있으면 추가로 stale·수기 편집된 `.kicad_pro`를 FAIL `regenerate` [kicad_pro], 리포트의 `project_hash`가 그 artifact와 다르면 FAIL `rerun_tool`(kicad.drc)로 판정; `review.manufacturing_capabilities`는 `check_capability`를 리뷰 시점에 다시 계산하고 각 한계값의 아카이브 페이지 해시·인용을 재검증한다(저장 판정과 다르거나 인용이 사라지거나 변조되면 FAIL `human`, 미아카이브는 `NOT_VERIFIED`); `review.requirements_vs_ir`는 추적할 설계 범주 요구사항이 없으면 `NOT_VERIFIED`(빈 설계는 추적된 설계가 아니다); `review.manufacturing_outputs`는 gerber/drill artifact의 신선도 + `mfg.*` 결과가 바로 그 파일 집합에 대해 실행되었는지(`artifact_hash` == 기록 해시; `mfg.*`는 실제 읽은 파일의 해시를 찍으므로 편집된 파일의 결과는 절대 맞지 않는다) 대조. 같은 반복 안에서 동일한 행위(예: `re-run kicad.drc`)를 두 리뷰 영역이 요구하면 한 번만 실행한다(`RepairStrategy.describe`).

`review.spice_vs_requirements`: 시뮬레이션 설정/netlist/결과가 없으면 `NOT_VERIFIED`; netlist artifact가 stale·디스크 불일치면 `regenerate`(SPICE_NETLIST); `SPICE_RESULT` artifact가 stale·디스크 불일치이거나 `spice` 결과·`results.json`의 netlist 해시가 현재 netlist와 다르면 `rerun_tool`(`spice`); 기대값이 FAIL이거나 이번 실행의 결과가 없거나 존재하지 않는 요구사항을 가리키거나 **기대값 nominal이 자기가 검증한다는 요구사항의 숫자 값과 다르면**(같은 단위, 기대값 허용치 이내여야 함 — 6 V 요구사항은 4 V nominal로 검증되지 않는다) `human`; 요구사항 값이 사용자가 타이핑한 문자열이면 `parse_answer`로 읽는다(텍스트 전체가 한 수량이어야 하며 `12 V max`·범위는 비교 불가 → `NOT_VERIFIED`; `details.quantity_version`에 파서 버전); `reduce == AT`이고 nominal에 단위가 없으면(ac 크기 비) 요구사항과 비교되는 것은 nominal이 아니라 sweep 점 `at`(요구사항과 같은 단위 — RC 템플릿의 |H(f_c)|는 사용자의 `cutoff_frequency`로 판정); netlist에서 제외된 부품이 검증된 요구사항을 섬기면 `details.excluded_serving`에 싣고 메시지에 `verified with D1 excluded: ...`를 덧붙인다; 요구사항에 비교할 숫자 값이 없거나 단위가 다르면 "traced but not compared"로 `NOT_VERIFIED`, netlist가 assumption 위에 있으면 `NOT_VERIFIED`; 모든 기대값이 현재 netlist에서 PASS이고 요구사항 값과 일치할 때만 PASS(rawfile·results.json Evidence, `requirement_id` 없는 기대값은 `details.untraced`) — 메시지는 "nominal 부품 값·단일 온도에서만 검증"임을 명시하고 `details.conditions`에 조건을 싣는다.

`review.calculations_vs_design`: provenance 형태 검사(도구·입력 존재) 뒤 리뷰어가 **직접** `recompute_parameters(ir)`를 돌려 그 판정을 통과시킨다(FAIL `human`+불일치 목록, NOT_VERIFIED+재계산 불가 목록); 현재 IR 해시에 대한 저장된 `calc.recompute` 결과와 판정이 다르면 그것도 FAIL(`human`).

SPICE: ngspice.dll은 프로세스 내 싱글턴이라 예기치 않은 access violation은 프로세스 재시작까지 엔진을 죽인다(`validate_deck`가 실측된 crash/poison 덱을 미리 거부); `.spiceinit`/`$SPICE_SCRIPTS/spinit`은 막지 않지만 init 직후의 `set` 목록과 그 해시가 `engine_info`로 모든 `results.json`·`spice` 결과에 남는다; `results.json`은 벡터 전체를 담으므로 긴 tran은 파일이 커진다; ngspice가 1 ULP 어긋나게 읽는 숫자는 `.cir.report.json`·`spice` details의 `inexact_numbers`로 보고할 뿐 거부하지 않는다(6자리 이하 데이터시트 값은 전부 정확); `ngspice_reads`의 13,975-철자 실험실 측정 자체는 저장소에 없고, 대신 측정 하니스와 500-철자 재측정 테스트 + 20개 고정값이 있다; `ac dec`의 격자점은 부동소수점상 정확하지 않으므로(1000.000000000002 Hz) 격자점 판정이 필요하면 `ac lin`을 쓰거나 허용치가 이웃 샘플의 간격보다 커야 한다. 2026-09-24 기능의 미측정 항목: `mfg.capability`는 kicad-cli의 프로젝트 규칙 적용이 측정될 때까지(`PROJECT_RULES_MEASURED_VERSIONS`가 비어 있다) PASS에 이르지 못한다 — 코드는 그 이유를 행마다 말한다; BOM `Value`/`Description`의 선행 `'`가 Excel/LibreOffice/fab importer에서 문자 그대로 보이는지는 실측하지 않았다(코드가 보장하는 것은 셀이 formula 문자로 시작하지 않는다는 것뿐); 템플릿 회로도의 ERC와 실제 KiCad `Device:LED`의 핀 이름(A/K)은 합성 라이브러리로만 테스트했고 실제 라이브러리에서는 실측하지 않았다(이름이 다르면 템플릿은 설계를 만들지 않는다); ATmega128 개발 보드(2026-09-27)의 ERC/DRC도 어느 머신에서도 실측하지 않았다 — 실제 KiCad 10.0.6 심볼의 핀 이름·번호·겹친 숨은 전원 핀(52/53/63)은 `KicadLibrary`로 읽어 확인했고, 회로도는 그 겹친 핀을 한 점으로 컴파일하지만 kicad-cli의 넷리스트·ERC로 확인하지 않았다; PLACEMENT가 배선한 보드의 실제 DRC는 어느 머신에서도 실측하지 않았다(`tests/test_pcb_agent.py`의 gated 테스트 둘: `pcb.routing=skip`으로 배선을 건너뛴 보드는 `unconnected_items`로 FAIL·exit 1, 배선된 분압기는 unconnected 0·clearance/폭/비아 위반 없음을 *기대*로 적어 두었다); 라우터가 올리는 한계값은 PLACEMENT 시점에 IR에 있는 것뿐이라 같은 실행의 FAB_CAPABILITY가 나중에 기록한 한계값은 `mfg.capability`/DRC로만 보드에 닿는다(다시 배선하지 않는다); 리포트의 KiCad 전용 행(kicad.erc/drc, mfg.gerber/drill과 그 Evidence)은 렌더링을 실측하지 않았다(같은 코드 경로이지만 gated 테스트가 없다).

ngspice-46(KiCad 번들 DLL)에 대해 실측으로 확인한 사실 (코드가 의존하는 것):

- `ngGet_Vec_Info`는 정적 구조체 하나의 포인터를 돌려주므로 다음 호출 전에 벡터를 복사해야 한다(러너는 즉시 `v_realdata[:n]`으로 복사).
- `ngSpice_Circ`(줄 배열 적재)는 `source`와 같이 `Circuit: <title>`을 출력하고 `listing`이 동작하며 plot에 title이 실린다 — 러너는 파일 경로를 ngspice 명령에 넣지 않고 한 번 읽은 바이트를 그대로 적재한다(`'`, `$`, 백틱이 든 폴더에서도 실행됨; rawfile `write`만 경로가 필요하다).
- `quit`은 ControlledExit(quit_exit=True)를 호출하고 DLL은 reset을 기다린다; `ngSpice_Reset` + `ngSpice_Init` + 설정 + 코드 모델 + 자체 테스트로 복구되어 이후 실행이 정상이다(테스트로 매 실행 검증).
- `ac lin 11 100 200`의 주파수 격자점은 정확한 double(150.0)이지만 `ac dec 10 1 1meg`의 격자점은 1 ULP 어긋난다(1000.000000000002): 격자점 판정에는 `lin`을 쓴다.
- 기본 분석 온도는 27 °C("Doing analysis at TEMP = 27.000000"); `.temp 127`은 `tc1=0.01` 저항을 두 배로 만든다(분압 6 V → 4 V 실측).
- 대화형 분석 명령은 소문자 장치 이름이어야 한다(`dc VVIN …`은 실패, `dc vvin …`은 성공) — `normalise_command`가 소문자화. `bg_<command>`는 전경 명령과 동일한 데이터를 주고 `bg_halt`로 중단 가능(워치독).
- 덱에 분석 카드가 있으면 `bg_<cmd>` 아래에서 무시되므로 `validate_deck`가 거부한다; `.control`/`.include`/`.lib`/따옴표/비ASCII도 거부(따옴표 불균형은 프로세스가 끝날 때까지 DLL을 오염시키고, 비접지 노드가 없는 회로는 access violation).
- 노드 이름은 `NODE_RE`(허용 문자 `A-Z a-z 0-9 _ . / + - : # @ [ ]`; 코드의 정규식은 `[A-Za-z0-9_./+\-:#@\[\]]+`)만 온전히 유지된다; 컴파일러가 같은 규칙으로 넷 이름을 거부한다.
- 반환 코드는 증거가 아니다(`ngSpice_Command`는 파싱 오류에도 0); 실패는 콜백(stderr 줄, ControlledExit, `No. of Data Rows` 부재, 새 plot 부재)으로만 판정.
- rawfile에는 `Date` 줄이 있어 바이트 동일성을 요구할 수 없다(증거: 경로+sha256). ASCII rawfile은 15자리, binary는 API 벡터와 비트 동일.
- 숫자 파서 `INPevaluate`는 정확히 반올림하지 않는다(가수 M × pow(10, E)): `10u` → 9.999999999999999e-06, `3.3` → 3.3000000000000003, 2^53 근처 홀수 가수 오독. `tools/calc/si.py`가 이를 모델링해 정확히 읽히는 철자를 고르고, 남는 것은 `inexact_numbers`로 보고한다.

kicad-cli 10.0.6에 대해 실측으로 확인한 사실 (코드가 의존하는 것):

- 종료 코드: 0 = 검사 실행됨(위반 유무 무관), 5 = `--exit-code-violations`이고 위반(warning 포함) 있음, 3 = 입력 로드 실패(리포트 없음), 1 = 잘못된 플래그/값, 2 = spice netlist에서 모델 라이브러리 없음(파일은 써짐 — 실측 사실일 뿐, `KicadCli._run`은 0/5 외의 종료 코드를 모두 실패로 취급하므로 그 파일을 쓰는 코드 경로는 없다).
- ERC 위반은 `sheets[].violations[]`, DRC는 `violations` / `unconnected_items`(severity error) / `schematic_parity` 세 리스트. 항목의 `type`·`severity`·`excluded`만 안정적이며 `description`과 stdout/stderr는 모두 로컬라이즈(한국어)된다 — 텍스트 매칭 금지. `--severity-all`은 사람이 제외한 위반도 `excluded: true`로 포함하며 우리는 그것도 error로 센다.
- `--schematic-parity`는 `<stem>.kicad_sch`가 보드 옆에 있어야 한다. 없으면 exit 0, stderr에 메시지, `schematic_parity: []` — 즉 조용히 "통과". `run_drc`는 sibling 부재를 `ToolExecutionError`로, 실행 후 비어있지 않은 stderr도 오류로 취급한다(성공 실행의 stderr는 항상 비어 있었다).
- ERC JSON의 `pos`는 실제 값의 1/100 (KiCad 버그, DRC는 정상). 위치를 쓸 일이 생기면 ×100.
- Gerber: 기본은 Protel 확장자(.gtl/.gbl/.gts/.gbs/.gm1 …), `--no-protel-ext`면 전부 `.gbr`. `<stem>-job.gbrjob`는 그 실행이 쓴 파일을 정확히 나열하므로 `export_gerbers`는 manifest로 결과 목록을 만든다. 헤더 `%TF.FileFunction`은 `Copper,L1,Top` / `Soldermask,Top` / `Profile,NP`, manifest는 `SolderMask,Top` / `Profile` 로 철자가 다르다. drill export는 구멍이 없는 보드에도 `<stem>.drl`(M48…M30)을 쓴다.
- 모든 export(gerber/drill/gbrjob/pos/netlist)에는 타임스탬프가 들어가므로 바이트 동일성은 우리가 컴파일한 `.kicad_sch`/`.kicad_pcb`에만 요구한다. artifact 해시는 "어떤 파일을 검사했는가"의 증거다.
- `pcb export pos`는 기본 단위가 inch, PosY는 보드 좌표의 부호 반전, `--smd-only`는 THT(핀 헤더) 제외 — CPL 대조에 쓸 때 주의(현재 리뷰어는 `pos` 대신 `.kicad_pcb`의 `(footprint (at ..) (layer ..))`를 직접 읽는다).
- `pcb drc --refill-zones`와 `pcb export gerbers --check-zones`는 stderr를 비운 채(parity 병행 시에도) 존을 메모리에서 채운다; 없으면 DRC는 존 동박을 못 보고(존만으로 이어진 GND는 `unconnected_items`) gerber에는 G36 영역이 전혀 없다.
- 하면 풋프린트의 `PAD::Flip(TOP_BOTTOM)`: `(chamfer top_left top_right)`는 `bottom_*`로, `(rect_delta x y)`는 y 반전, custom `primitives`는 y 반전, 나머지 스칼라 유지 — 각각 `lib_footprint_mismatch` warning 유무로 실측(L_Bourns_SDR0604, Analog_QFN-28-36-2EP, AMS_LGA-10-1EP, BatteryHolder_Keystone_1057).
