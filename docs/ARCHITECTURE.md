# Architecture

이 문서는 프로젝트 사양의 각 섹션이 코드의 어디에 대응되는지, 그리고 스캐폴드가 강제하는 불변식(invariant)이 무엇인지 정리합니다.

## 1. 불변식

1. **IR이 유일한 원본.** `.kicad_sch`, `.kicad_pcb`, BOM, CPL, netlist, Gerber는 전부 `ArtifactRef`로 등록되는 파생물이며 `generated_from_ir_hash`를 갖는다. `CircuitIR.content_hash()`는 **design view**(`model_dump(context={"view": "design"})`; 각 모델이 `drop_in_design_view`로 자기 필드를 뺀다 — 키 이름이 아니라 필드가 기준)만 해시한다: `validation`/`artifacts`(설계에 *대한* 상태), `project.workdir`/`project.created_at`(어디서·언제 만들었는가), `requirements.extraction_cache`(모델이 말한 것의 메모 — 2절 참조), 모든 `Provenance.created_at`(기본값이 현재 시각)과 `SourceRef`/`RegulatoryProvenance`의 `retrieved_at`(가져온 시각), 위치를 가리킬 뿐인 `SourceRef.document_path`·`LibraryRef.library_path`·`RegulatoryProvenance.source_document`(사본은 `content_hash`가, 라이브러리 항목은 verbatim 임베드와 ERC의 `lib_*_mismatch`가 고정한다), 그리고 규제 검증의 *결과*인 `RegulatoryRequirement.status`/`source_status`·`RegulatoryProvenance.verification_status`·`GroundedQuote.found`/`page`/`context`/`reason`(오프라인 실행과 온라인 실행이 다르게 채우는 것; 같은 이유로 `RegulatoryProvenance.section`·`applicability_rationale`은 규칙이 인용하는 절과 읽은 입력만 담고 페이지나 grounded 여부는 담지 않는다)를 제외한 **설계 내용만** — 같은 설계를 다른 폴더에서 다른 시각에 다른 KiCad 설치본으로 다시 만들거나 JSON에서 다시 읽어도 해시가 같다(`tests/test_spice_findings_regressions.py`, `tests/test_md_review_findings_regressions.py`). `SourceRef`·`RegulatoryProvenance`·`GroundedQuote`의 `content_hash`/`source_url`(어떤 문서를 썼는지)과 `GroundedQuote.quote`(어떤 주장인지)는 provenance이므로 해시에 남고 — 그래서 규제 문서의 *첫 성공 fetch*만이 해시를 움직이고 같은 사본을 다시 쓰는 실행은 움직이지 않는다 — 사용자가 `created_at`이라는 이름을 붙인 파라미터는 설계 내용이라 해시된다. `Traced` 값의 inf/NaN은 JSON이 담지 못하므로(`null`로 저장되어 다시 읽히지 않는다) 모델 경계에서 거부되고 `CircuitIR.load`는 비표준 `Infinity`/`NaN` 토큰을 `IRSchemaError`로 거부한다(`tests/test_md_review_findings_regressions.py` 60).
2. **모든 중요한 값은 `Traced[T]`.** 값 + 단위 + `Provenance(kind, source, derived_from, inputs, tool, tool_version, note)`. `llm_generated`/`assumption`은 `needs_verification=True`. `derived` 값은 계산기가 직접 `inputs`(역할 → id)를 기록하므로 재계산은 위치가 아니라 역할로 호출을 재구성한다.
3. **검증 상태는 boolean이 아니다.** `worst_status([])`는 `NOT_VERIFIED`이다. 증거가 없으면 PASS가 아니다.
4. **도구가 붙지 않은 ValidationResult는 의견이다.** `ValidationResult.tool`이 있어야 tool-backed. ERC/DRC 결과는 `tools/kicad/cli.py`만 생성하며 KiCad 버전·리포트 경로·검사 대상 파일 해시를 함께 기록한다.
5. **Agent는 설계 내용을 직접 수정하지 않는다.** `AgentResult.proposals: list[IRProposal]`를 돌려주고, `Orchestrator.apply_proposals()`가 설계 내용(design view에 드는 것)의 유일한 적용 지점이다(향후 GUI 확인/diff 훅). 페이로드는 대상 필드의 타입으로 검증된다(`topology`에 dict를 주면 `Topology`가 되거나 거부되고, `components`에 문자열을 주면 거부된다 — 오늘 해시되고 내일 로드되지 않는 IR은 만들어지지 않는다); `remove`는 설계 내용(`created_at` 제외)으로 대조하고 아무것도 지우지 못하면 오류다. artifact·validation 기록(`ir.artifacts`, `ir.validation`)은 설계가 아니므로 단계 러너·SPICE 단계(`SimulationAgent`, `run_spice_for`)·수리 전략이 직접 쓴다. 제안은 증거가 아니다: 검증 결과 없이 제안만 낸 단계는 `NOT_VERIFIED`("N proposal(s) applied, nothing verified")이지 PASS가 아니다.
6. **수리는 재생성 또는 재실행뿐.** `repair/strategies.py`의 `RegenerateArtifact`, `RerunTool`. `NON_REPAIRABLE` 카테고리(`human`, `regulatory_conflict`, `unverified_component_data`, `fab_capability_shortfall`, `circuit_structure_change`)는 `NotRepairableError`로 거부되고 `RepairOutcome.unresolved`에 사유와 함께 보고된다. `RepairLoop`는 모든 행위 전후로 IR 해시를 직접 재고, 해시가 바뀐 행위는 실패("changed the design")로 기록하고 루프를 중단한다(`stopped_reason = "repair strategy mutated the IR"`). oscillation 지문은 IR 해시 + 실패 검사 id와 그 수리 범주 + artifact 해시라서 재실행이 stale 리포트를 진짜 위반(`human`)으로 바꾼 것은 반복이 아니라 사람에게 넘길 진전이고, 실패한 행위는 루프가 진전한 다음 반복에서 다시 시도된다(재생성 뒤의 재실행); 행위가 하나라도 실패한 결과는 PASS가 아니라 `NOT_VERIFIED`다. 모든 시도(전략, 설명, 전후 해시, 오류, 시각)는 `RepairAgent`가 `repair.loop` ValidationResult의 `details.actions`로 IR에 남긴다(설계 해시 밖).
7. **외부 행위는 승인 필요.** `security.require_approval(ExternalAction, detail)` — 승인은 1회용·행위+세부내용 단위이며 일반화되지 않는다. 네트워크 fetch도 외부 행위다(`NETWORK_FETCH`, CLI `--online`이 "online session" 승인을 1회 grant+consume); 승인 없이는 소켓이 열리지 않고(`tools/sources/archive.py`의 `fetch`는 요청을 만들기 전에 `ApprovalRequiredError`), 승인이 있어도 신뢰 origin(KiCad 라이브러리 Datasheet 호스트, 규제 후보 목록의 공식 도메인, 사용자가 준 호스트/정확한 URL — 포트는 origin의 일부라 443이 아닌 포트는 사용자가 준 정확한 URL로만)만, https만, URL당 실행당 1회만 fetch한다. 모델이 말한 URL은 호스트만으로는 절대 신뢰되지 않는다: 규제 제안(`ProposedRegulation`)의 URL은 그 호스트가 후보 목록의 공식 도메인 allow-list에 있고 사용자가 `accept_regulations`로 수락했을 때만, fetch 시점에 allow-list를 다시 확인한 뒤 fetch된다(IR에 저장된 `refused` 필드를 믿지 않는다).
8. **KiCad 위반은 심각도와 무관하게 FAIL.** `tools/kicad/cli.py`는 error든 warning이든(사람이 exclusion 처리한 것 포함) 위반이 하나라도 있으면 `FAIL`을 낸다(`details.warning_policy`). warning을 PASS 뒤에 숨기면 `lib_symbol_mismatch`/`lib_footprint_mismatch` 같은 컴파일러 결함도 숨겨진다. 리포트의 컨테이너 키(`sheets[].violations`, `violations`, `unconnected_items`)가 없으면 "0 violations"가 아니라 `ToolExecutionError`다.
9. **레이아웃도 추적된다.** `Placement`/`Track`/`Via`/`Zone`은 `provenance`를 가진다(기본값은 `assumption` "origin not recorded"). `route_naive`는 `derived`/`routing.naive`를 스탬프한다. `review.ir_vs_pcb`는 검증이 필요한(unrecorded/assumption/llm_generated) 레이아웃 항목이 있으면 `NOT_VERIFIED`다. `Net.serves_requirements`로 패드→넷→요구사항 사슬이 이어진다.
10. **모델 출력은 제안이고, 사용자가 본 것만 확인할 수 있다.** LLM이 돌려준 것은 strict 스키마로 파싱된 뒤 결정론적으로 대조되어야 IR에 들어가고, 그때도 `llm_generated`다(`llm/extraction.py`). `user_requirement`가 되는 길은 (a) 사용자가 `--answer`로 직접 준 값, (b) 요청문 인용으로 grounding된 explicit 항목을 사용자가 **이전 실행에서 표로 본 뒤** `confirm_requirements`로 확인한 것, (c) 모델의 implicit/assumption 항목을 사용자가 `accept_implicit`로 개별 수락한 것뿐이다. 같은 규칙이 부품 후보(`confirm_parts`, 행 단위: 이전 표에 있던 행만)와 모델의 데이터시트 사실(`confirm_facts`: grounding은 인용·수량·단위 계열·주문표 행을 대조하지만 모델이 숫자에 붙인 *의미*는 대조하지 못하므로, 표를 본 사용자의 확인 전에는 IR에 아무것도 없다)에 적용된다. 결정되지 않은 `llm_generated` 요구사항은 `ir.llm_requirements`가 `USER_INPUT_REQUIRED`로 IR_BUILD를 막고, 리뷰어는 그것을 강제하지도(unserved FAIL 없음) 충족된 것으로 세지도 않는다(`NOT_VERIFIED`). 예산은 승인이며 **사전 조건**이다: 지출이 예산에 *도달*하면 다음 요청은 거부되고, 모든 요청에 `max_tokens`가 실린다(`llm/service.py`).
11. **부품 identity는 아카이브된 데이터시트가 만든다.** MPN이 authoritative로 *표시*된 것은 증거가 아니다. `parts/identity.py` `mpn_grounding`(IR_BUILD의 `ir.component_provenance`와 리뷰어의 `review.component_provenance`가 같은 함수를 쓴다)은 MPN의 provenance가 `authoritative`이고 그 `SourceRef`가 **아카이브 항목**(`<sha256>.meta.json`이 있는 디렉터리의 파일: 실행의 archive, `<workdir>/sources`, 또는 기록된 경로 자신의 디렉터리)을 가리키며(해시가 맞는 임의의 파일은 `unarchived` — 어디서 왔는지 아무것도 증명하지 않는다), 그 파일이 지금도 그 해시로 재해시되고, 현재 추출기의 텍스트가 meta에 기록된 텍스트 해시와 같고(아니면 `re-extracted`), 그 문서가 PDF이며(HTML 제품 페이지는 `not a datasheet`), **검사 시점에 MPN을 기록된 페이지에서 직접 다시 찾을 때만**(없으면 `not in text`; `page N`이 기록되지 않았으면 `no page recorded`) grounded로 본다 — 표시만 된 값은 `NOT_VERIFIED`(사유 기록), 변조된 파일은 `tampered`. `Component.mpn_tagged_authoritative`는 태그의 존재만 말하는 속성이지 grounding 검사가 아니다. MPN은 `component.existence.<ref>`가 아카이브된 PDF 본문에서 verbatim(대소문자·공백 무시, 온전한 식별자 — `LM2596S-5`는 `LM2596S-5.0/NOPB`에서 발견되지 않는다)으로 찾았을 때만 `ComponentAgent`가 authoritative로 재태깅한다(못 찾으면 `NOT_VERIFIED`, 절대 FAIL·추측 없음; note에 추출기·버전·텍스트 해시 스탬프). BOM의 `DatasheetHash` 열이 그 사본의 sha256을 싣는다.
12. **규제 단계는 출처와 적용 여부만 말한다.** `regulatory.compliance`는 항상 `NOT_VERIFIED`(엔지니어/인증기관이 판정)이고, `regulatory.sources`의 PASS는 정확히 "공식 문서를 아카이브했고 큐레이션 목록이 주장한 인용을 전부 그 본문에서 찾았다"이며, 인용을 못 찾으면 목록이 틀린 것이므로 FAIL이다. 적용 여부는 선언적 규칙 + 사용자의 범위 답변 + IR 요구사항으로 결정론적으로 판정되되 **`user_requirement`/`authoritative` provenance의 요구사항만 읽고**(모델 추출·가정·derived 값은 확인 또는 직접 답변을 요구하는 `USER_INPUT_REQUIRED`), 전압 규칙은 장비의 정격(`input_voltage`·`output_voltage` 요구사항 + 사용자의 `highest_rated_voltage`)으로 판정한다 — 하나라도 대역 안이면 적용, `NOT_APPLICABLE`은 전부 밖이고 최고 전압 답이 있을 때만; yes/no 질문에 yes/no가 아닌 답은 미결; 규칙이 다루지 않는 제외 조항은 항목의 `not_evaluated`로 rationale과 메시지에 실린다. 리뷰어 `review.regulatory_provenance`는 10개 provenance 필드·아카이브 항목인 해시 일치 파일·**모든 발견 인용의 리뷰 시점 재탐색**·결정된 적용 여부를 요구하며 모든 메시지에 "compliance not assessed"를 쓴다.

## 2. 사양 섹션 ↔ 모듈

| 사양 | 모듈 |
|---|---|
| 4. 요구사항 기반 설계 / 누락 정보 질문 | `ir/requirements.py` (`RequirementSet` — `raw_input` + 사용자 `corrections`(설계 내용, 해시됨) + `extraction_cache`(모델이 말한 것의 메모, IR 파일에는 있으나 **설계 해시에서 제외**), `MissingInformation`(`source="system"\|"llm"` — 모델이 쓴 질문은 CLI가 `(model question)`으로 표시)), `agents/requirement.py` (LLM 없음: 기본 질문 체크리스트만 — 종전과 동일; LLM 있음: 추출 → 결정론적 grounding → 제안 → `confirm_requirements` 확인 게이트 → `accept_implicit`/`reject_implicit` 개별 결정, 아래 "신뢰 모델"), `tools/calc/quantity.py` (결정론적 공학 수량 파서: `M`=mega, `m`은 단위 앞에서만 milli, 단위는 절대 추측하지 않음(`mAh`·`°F`·맨 접두사는 `None`), 범위 규칙 `1-10 kΩ`=1k..10k / `12-5V`는 범위 아님, `±`는 `plus_minus`, 한국어 조사 허용), `llm/extraction.py` (strict 스키마 `RequirementExtraction` + `ground_extraction`: explicit 항목은 요청의 **verbatim 인용**을 `find_quote`가 문자 단위(`m`≠`M`)로 **토큰 경계**에서 찾고(`5V`는 `-5V`·`0.5A`·`12V`·`5Vin` 안에서 발견되지 않음, 한글 조사는 붙어도 됨), 값은 모델의 복사본이 아니라 **요청의 그 자리 텍스트**를 수량 파서로 읽되 `find_quantities`가 요청 전체에서 거기에 읽는 수량과 같아야 하며(`3.3 to 5 V`의 `5 V`는 범위의 일부라 거부), 모델의 number/unit이 그 값과 rel 1e-9로 일치해야 통과 — 아니면 assumption으로 **강등**(사유 기록); `±5 %`는 `[-5, 5]` 대칭 범위로 진입하고 `_mismatch`가 `±`를 대조; explicit 항목의 `text`는 사용자의 말(`<key>: <인용>`)이고 모델의 문장은 note에만(예외: application 항목은 값이 모델의 요약이고 인용은 note에 — 확인 표의 "in your request"가 그것을 잡으며, 확인 후 규제 단계의 `intended_use`가 된다); implicit은 rationale 필수·`llm_generated` 유지; 지시문 구절(`ignore previous`, `prior instructions`, `everything above`, `api key`, `이전 안내`, `키를 알려` …)이 든 항목은 **drop** — 심층 방어이지 방어선이 아니다(실행되는 것은 없고, 사람에게 닿는 모델 문장은 표시된다); 키 canonical snake_case, 값이 같은 중복은 하나로 병합하되 grounding된 explicit 항목이 살아남고(모델이 나열한 순서와 무관), 값이 없는 중복은 **같은 종류끼리만** 병합, 숫자가 다르면 `RequirementConflict`, **종류가 다르면 값이 옮겨가지 않고** `req.<key>.<kind>`로 분리(모델의 숫자가 explicit 항목을 타고 `user_requirement`가 될 수 없음); 즉 `user_requirement`가 되는 것은 (a) 사용자가 `--answer`로 직접 준 값, (b) 요청문 인용으로 grounding된 explicit 추출 항목을 사용자가 표로 본 뒤 `confirm_requirements`로 확인한 것, (c) 모델의 implicit/assumption 항목을 사용자가 `accept_implicit`로 개별 수락한 것뿐이다. 모델의 implicit 추론과 assumption, grounding에 실패한 주장은 확인해도 `llm_generated`/`assumption`으로 남는다(사용자는 자기가 *말한 것*을 확인한 것이지 모델의 추론을 확인한 것이 아니다). 대조되지 **않는** 것은 모델이 인용에 붙인 key와 category다 — `12V`를 `output_voltage`로 분류한 것은 그대로 12 V로 grounding되며, 확인 표의 "in your request" 열(인용 앞뒤 20자)이 사람이 그것을 잡는 유일한 곳이다. `extraction_cache`는 IR 파일에 저장되지만 `content_hash`에서 제외되고(모델이 말한 것은 설계가 아니다), `corrections`는 사용자의 말이므로 해시에 들어간다(`tests/test_requirement_agent_llm.py::test_extraction_cache_is_not_design_content_but_corrections_are`). CLI `run`은 파이프라인이 어디서 죽든 `finally`에서 IR을 저장하고 LLM 사용량을 출력하므로 유료 추출이 나중 단계의 결함에 사라지지 않는다.

SPICE 단계의 상태 규칙 (`SimulationAgent` + `tools/spice/stage.py`): `ir.simulation` 없음 / 엔진 없음 / 바인딩된 부품 없음(`NothingToCompileError`) → `NOT_VERIFIED`; 컴파일러가 거부(`CompileError`: 바인딩 없는 부품, `llm_generated` 값·컨테이너, 떠 있는 핀, `electrical`과 다른 SPICE 값 …) → `FAIL`(human); 분석이 실패(ngspice stderr, ControlledExit, 타임아웃 …) → `spice` `FAIL`(human, ngspice의 오류 줄 포함) — 단, *환경*이 막은 경우(`SpiceResult.unverifiable`: rawfile을 쓸 곳이 없음, 죽은 엔진, 코드 모델 미적재 + `A` 소자)는 `NOT_VERIFIED`(설계에 대한 판정이 아님); 기대값은 `|measured − nominal| ≤ max(tol_abs, tol_rel·|nominal|)`로 판정(허용치 없음, 또는 `nominal == 0`에 `tol_rel`만 → `UNRESOLVED`, 벡터 없음 → `FAIL` "vector not produced"); `at`이 샘플 사이에 있으면 보간(dc/tran 선형, ac는 log-주파수·크기 벡터는 log-log)하되 두 이웃 샘플이 `details.bracket`에 기록되고 **두 이웃 모두 허용치 안일 때만 PASS**, 둘 다 같은 쪽으로 밖이면 FAIL, 그 사이면 `UNRESOLVED`("grid too coarse") — 보간 오차가 설계 편차로 보고되지 않는다; netlist가 `assumption` 값/결정 위에 서 있으면 PASS 대신 `NOT_VERIFIED`(FAIL은 FAIL); 요약 `spice`는 기대값 결과의 최악값(기대값이 없으면 `NOT_VERIFIED`); 모든 결과에 `conditions`(부품 값 nominal, 온도 `.temp` 또는 ngspice 기본 27 °C, 코너 미시뮬레이션)와 엔진 스탬프(빌드·코드 모델·설정 해시)가 붙는다; 설정에서 제거·개명된 기대값의 옛 `spice.<id>`는 `NOT_APPLICABLE`로 대체되어 RELEASE를 막지 않는다.

컴파일 단계의 상태 규칙 (`Orchestrator._compile`, BOM/CPL·gerber/drill 포함): 판정은 tool-backed `compile.<kind>` ValidationResult로 `ir.validation`에 남는다(PASS는 쓴 artifact의 해시, FAIL은 `repair: human`) — RELEASE·`ai-eda run`의 종료 코드·`ai-eda review`가 그것을 읽는다; `NothingToCompileError`(부품 없음, `ir.pcb` 없음, 내보낼 PCB artifact 없음)·`NotImplementedError`(아직 없는 컴파일러) → `NOT_VERIFIED`; 그 외 `CompileError`(핀 불일치, 미검증 심볼/풋프린트, 넷에 없는 핀 …) → `FAIL` + 메시지; 다른 예외는 결함이므로 전파. 거부된 종류의 오래된 artifact는 증거로 남지 않도록 제거한다. 빈 회로도는 ERC를 "0 violations"로 통과하므로, 부품이 없는 IR은 회로도를 아예 쓰지 않는다.

## 4. 리뷰어가 FAIL을 내는 방식과 수리 매핑

| 리뷰 결과 `details` | 전략 |
|---|---|
| `{"repair": "regenerate", "artifact": <ArtifactKind>}` 또는 `"artifacts": [...]` | `RegenerateArtifact` → 등록된 컴파일러/exporter로 재생성 (한 행위로 여러 종류; `CompileError`·도구 부재는 실패한 행위로 보고) |
| `{"repair": "rerun_tool", "tool_check": "kicad.erc"\|"kicad.drc"\|"spice"\|"mfg.gerber"\|"mfg.drill"}` 또는 `"tool_checks": [...]` | `RerunTool` → kicad-cli 재실행 / `run_spice_for` 재실행(fresh한 netlist에만) / 출력 형식 검사 재실행 |
| `{"repair": "human"}` 등 `NON_REPAIRABLE`, 또는 `repair` 키 없음 | 거부, `unresolved`에 보고 |

리뷰어가 증거를 읽는 방식: `review.ir_vs_*`는 `ArtifactRef.is_stale`/`matches_disk`(다중 파일 artifact는 `files` 집합 해시), `review.ir_vs_pcb`는 추가로 레이아웃 항목의 provenance(불변식 9); `review.pcb_vs_bom` / `review.pcb_vs_cpl`은 (1) CSV의 reference/designator 집합이 IR과 같고 (2) CSV가 stale이 아니며 (3) 디스크 해시가 기록과 같고 (4) 보드 artifact가 있고 fresh·디스크 일치일 때 `tools/kicad/board.py`로 읽은 보드 풋프린트와 행 단위로 대조한다(BOM: reference·Value·Footprint id, CPL: 위치 1e-4 mm·회전(정규화)·면) — (1)~(3) 위반은 `regenerate`(BOM/CPL), (4)의 stale 보드는 `regenerate`(PCB), 보드 없음은 `NOT_VERIFIED`, fresh한 둘이 불일치하면 컴파일러 결함이므로 `human`; 결과에는 CSV와 보드의 경로·디스크 해시가 `Evidence`로 붙는다. `review.schematic_vs_pcb`는 최신 `kicad.drc`가 (a) 현재 보드에서 실행되었고 (b) parity를 실제로 평가했으며 (c) 현재 회로도(`schematic_hash`)에 대해 평가했고 (d) parity 항목이 0개일 때만 PASS — parity 항목은 KiCad 심각도가 warning이어도 FAIL(`human`); `review.erc`/`review.drc`는 도구 결과를 그대로 통과시키되(tool이나 artifact 해시가 없는 결과는 의견이라 `NOT_VERIFIED`; `review.manufacturing_capabilities`·parity도 같다) FAIL이면 `human` + 위반 타입 목록; `review.requirements_vs_ir`는 추적할 설계 범주 요구사항이 없으면 `NOT_VERIFIED`(빈 설계는 추적된 설계가 아니다); `review.manufacturing_outputs`는 gerber/drill artifact의 신선도 + `mfg.*` 결과가 바로 그 파일 집합에 대해 실행되었는지(`artifact_hash` == 기록 해시; `mfg.*`는 실제 읽은 파일의 해시를 찍으므로 편집된 파일의 결과는 절대 맞지 않는다) 대조. 같은 반복 안에서 동일한 행위(예: `re-run kicad.drc`)를 두 리뷰 영역이 요구하면 한 번만 실행한다(`RepairStrategy.describe`).

`review.spice_vs_requirements`: 시뮬레이션 설정/netlist/결과가 없으면 `NOT_VERIFIED`; netlist artifact가 stale·디스크 불일치면 `regenerate`(SPICE_NETLIST); `SPICE_RESULT` artifact가 stale·디스크 불일치이거나 `spice` 결과·`results.json`의 netlist 해시가 현재 netlist와 다르면 `rerun_tool`(`spice`); 기대값이 FAIL이거나 이번 실행의 결과가 없거나 존재하지 않는 요구사항을 가리키거나 **기대값 nominal이 자기가 검증한다는 요구사항의 숫자 값과 다르면**(같은 단위, 기대값 허용치 이내여야 함 — 6 V 요구사항은 4 V nominal로 검증되지 않는다) `human`; 요구사항에 비교할 숫자 값이 없거나 단위가 다르면 "traced but not compared"로 `NOT_VERIFIED`, netlist가 assumption 위에 있으면 `NOT_VERIFIED`; 모든 기대값이 현재 netlist에서 PASS이고 요구사항 값과 일치할 때만 PASS(rawfile·results.json Evidence, `requirement_id` 없는 기대값은 `details.untraced`) — 메시지는 "nominal 부품 값·단일 온도에서만 검증"임을 명시하고 `details.conditions`에 조건을 싣는다.

`review.calculations_vs_design`: provenance 형태 검사(도구·입력 존재) 뒤 리뷰어가 **직접** `recompute_parameters(ir)`를 돌려 그 판정을 통과시킨다(FAIL `human`+불일치 목록, NOT_VERIFIED+재계산 불가 목록); 현재 IR 해시에 대한 저장된 `calc.recompute` 결과와 판정이 다르면 그것도 FAIL(`human`).

검증된 시나리오(`tests/test_vertical_slice.py`): 실행 후 R3(10k, VOUT→GND)를 넷·배치·트랙·SPICE 바인딩과 함께 추가하고 R1을 5k로 바꿔(R2‖R3 = 5k) 요구사항 6 V/3 V가 그대로 성립하게 하면(기대값 nominal은 계산기로 재산출) `ir_vs_schematic / ir_vs_pcb / pcb_vs_bom / pcb_vs_cpl / manufacturing_outputs / spice_vs_requirements`가 `regenerate`로 FAIL → 1회차에 6종 재생성 → 2회차에 ERC/DRC/SPICE/출력 검사 재실행 → 3회차 리뷰 전부 PASS, IR 해시 불변. `tests/test_simulation_stage.py`: 잘못된 nominal(5 V)은 `spice.v_out` FAIL → 리뷰 `human` → 루프가 unresolved로 보고; R1을 20k로 바꾸면 `regenerate` → netlist 재생성 → `rerun_tool` → ngspice 재실행 → 기대값이 정직하게 FAIL(4 V vs 6 V, human)이고 stale한 저장 파라미터는 `calculations_vs_design`도 잡는다; nominal**과 요구사항**을 함께 갱신하면 같은 루프가 2회차에 PASS로 수렴; `results.json` 수기 편집은 `rerun_tool`로 감지·재실행; stale netlist에 대한 `RerunTool`은 거부. `tests/test_spice_findings_regressions.py`: nominal만 재산출하고 요구사항을 두면 리뷰가 `human`으로 거부, 제거된 기대값은 RELEASE를 막지 않음, assumption 값은 어디서도 PASS가 되지 않음, `O'Brien` 같은 workdir도 실행됨, ControlledExit 복구, 파서 모델 500-철자 재측정 등 24건. `tests/test_findings_regressions.py`: 배치 이동만으로 CPL이 FAIL(`regenerate`), CSV 수기 편집 FAIL, 보드와 행 불일치 FAIL(`human`), 보드 없음 NOT_VERIFIED.

1. ~~**Datasheet/부품 데이터 파이프라인**~~ — 완료(위). 남은 것: SPICE 모델 카드를 데이터시트/벤더 모델에서 authoritative `model_card`로 가져오는 경로, 실 제조사 사이트에 대한 gated 측정(`AI_EDA_ONLINE=1`), 라이브러리 핀·패키지를 데이터시트 값과 대조하는 grounding(현재는 MPN·사실 값만), AES 암호화 PDF(`cryptography`).
2. **LLM 설계 제안** — `CircuitDesignAgent`/`PCBAgent`가 IR 제안(배치·트랙·`SpiceBinding`·`SimulationSetup` 포함)을 내고 컴파일러+DRC+SPICE가 판정(`llm_generated` 값은 netlist 컴파일러가 거부하므로 제안은 검증 후에만 시뮬레이션에 도달). 실 모델의 grounding 성공률을 `tests/test_openrouter_live.py`류의 gated 측정으로 기록.
3. **전원 심볼/PWR_FLAG와 `.kicad_pro` 설계 규칙** — POWER/GROUND 넷에 `power:*` 심볼 emit, `compilers/pcb.py`의 `design_rules(ir)`를 프로젝트 파일로 써서 fab 한계값이 실제 DRC 규칙이 되게.
4. ~~**규제 조사 파이프라인**~~ — 출처·적용 여부까지 완료(위). 남은 것: KR 적합성평가 고시의 URL·인용 확보(law.go.kr DRF `target=admrul` 프로브), 실 사이트 gated 측정(`AI_EDA_ONLINE=1` 테스트 3건은 있으나 이 머신에서 실행되지 않았다), 아카이브의 호스트별 요청 간격(EUR-Lex WAF는 짧은 시간의 ~13건 이상 요청에 202 challenge — 지금은 blocked/error → NOT_VERIFIED로 정직하게 보고될 뿐 pacing은 없음), 규칙이 `not_evaluated`로만 명시하는 제외 조항(LVD Annex II의 나머지, RoHS Article 2(4) 등)을 답변 규칙으로 모델링하는 것.
5. **JLCPCB capability 수집** — 공식 페이지 → authoritative `ManufacturingConstraints`.
6. **GUI** — `PipelineState`/`ReviewReport`/`RepairOutcome`를 그대로 노출.

ngspice-46(KiCad 번들 DLL)에 대해 실측으로 확인한 사실 (코드가 의존하는 것):

- `ngGet_Vec_Info`는 정적 구조체 하나의 포인터를 돌려주므로 다음 호출 전에 벡터를 복사해야 한다(러너는 즉시 `v_realdata[:n]`으로 복사).
- `ngSpice_Circ`(줄 배열 적재)는 `source`와 같이 `Circuit: <title>`을 출력하고 `listing`이 동작하며 plot에 title이 실린다 — 러너는 파일 경로를 ngspice 명령에 넣지 않고 한 번 읽은 바이트를 그대로 적재한다(`'`, `$`, 백틱이 든 폴더에서도 실행됨; rawfile `write`만 경로가 필요하다).
- `quit`은 ControlledExit(quit_exit=True)를 호출하고 DLL은 reset을 기다린다; `ngSpice_Reset` + `ngSpice_Init` + 설정 + 코드 모델 + 자체 테스트로 복구되어 이후 실행이 정상이다(테스트로 매 실행 검증).
- `ac lin 11 100 200`의 주파수 격자점은 정확한 double(150.0)이지만 `ac dec 10 1 1meg`의 격자점은 1 ULP 어긋난다(1000.000000000002): 격자점 판정에는 `lin`을 쓴다.
- 기본 분석 온도는 27 °C("Doing analysis at TEMP = 27.000000"); `.temp 127`은 `tc1=0.01` 저항을 두 배로 만든다(분압 6 V → 4 V 실측).
- 대화형 분석 명령은 소문자 장치 이름이어야 한다(`dc VVIN …`은 실패, `dc vvin …`은 성공) — `normalise_command`가 소문자화. `bg_<command>`는 전경 명령과 동일한 데이터를 주고 `bg_halt`로 중단 가능(워치독).
- 덱에 분석 카드가 있으면 `bg_<cmd>` 아래에서 무시되므로 `validate_deck`가 거부한다; `.control`/`.include`/`.lib`/따옴표/비ASCII도 거부(따옴표 불균형은 프로세스가 끝날 때까지 DLL을 오염시키고, 비접지 노드가 없는 회로는 access violation).
- 노드 이름은 `NODE_RE`(허용 문자 `A-Z a-z 0-9 _ . / + - : # @ [ ]`; 코드의 정규식은 `[A-Za-z0-9_./+\-:#@\[\]]+`)만 온전히 유지된다; 컴파일러가 같은 규칙으로 넷 이름을 거부한다.
- 반환 코드는 증거가 아니다(`ngSpice_Command`는 파싱 오류에도 0); 실패는 콜백(stderr 줄, ControlledExit, `No. of Data Rows` 부재, 새 plot 부재)으로만 판정.
- rawfile에는 `Date` 줄이 있어 바이트 동일성을 요구할 수 없다(증거: 경로+sha256). ASCII rawfile은 15자리, binary는 API 벡터와 비트 동일.
- 숫자 파서 `INPevaluate`는 정확히 반올림하지 않는다(가수 M × pow(10, E)): `10u` → 9.999999999999999e-06, `3.3` → 3.3000000000000003, 2^53 근처 홀수 가수 오독. `tools/calc/si.py`가 이를 모델링해 정확히 읽히는 철자를 고르고, 남는 것은 `inexact_numbers`로 보고한다.
- Ubuntu 24.04 `libngspice0`(ngspice-42, 2024-03-31 빌드; `NGSPICE_DLL=/usr/lib/x86_64-linux-gnu/libngspice.so.0`)에 대한 실측 2026-09-23: `ngSpice_Reset`을 export하지 않는다(ngspice 44 이후에 추가) — 러너는 선택적으로 바인딩하고, 없으면 ControlledExit 뒤 복구 대신 프로세스가 끝날 때까지 엔진을 죽은 것으로 표시하며 `engine_info()["reset_supported"]`와 `doctor`가 그렇게 말한다; 분석마다 `Using SPARSE 1.3 as Direct Linear Solver`를 **stderr**로 출력한다(정보성 — `INFORMATIONAL_STDERR_RE`로 분류해 transcript에는 남기되 오류로 세지 않는다); rawfile에 `Command:` 줄이 없다(46은 `ngspice-46, Build …`; 파서는 그 줄을 선택으로 본다); 코드 모델 6종은 `/usr/lib/x86_64-linux-gnu/ngspice/*.cm`; `ngspice_reads` 모델은 하니스 표본 500개 전부와 고정값 4개가 46과 동일하게 읽힌다 — 단 맨 `a`/`A` 꼬리(`2A`)는 42가 atto(2e-18)로 읽으므로 모델은 그 철자를 보증하지 않고(`None`) 포맷터는 쓰지 않는다; `4k7`·`1e+`는 42가 4000·1로 말없이 읽는다(그래서 엄격 파서가 거부). 이 빌드로 SPICE 단계·기대값 판정·rawfile 왕복 테스트가 모두 통과한다(Linux 전체 1053 passed / 80 skipped, KiCad 없이·라이브러리 자동 탐색). KiCad 10은 Linux에서 아직 측정되지 않았다(Ubuntu 24.04 apt의 `kicad`는 7.0.11로 20260206 보드 형식을 읽지 못한다; KiCad PPA는 이 컨테이너에서 차단됨).
- kicad-cli `sch export netlist --format spice`는 GND를 노드 이름으로 유지하고 모델 없는 심볼에 `__<ref>` 자리표시자를 쓴다(ngspice가 전체 파일을 거부); 심볼에 `(exclude_from_sim yes)`를 주면 사라진다(`dnp`는 무관) — 회로도 컴파일러가 바인딩 없는/제외된 부품에 이를 emit한다.

kicad-cli 10.0.6에 대해 실측으로 확인한 사실 (코드가 의존하는 것):

- 종료 코드: 0 = 검사 실행됨(위반 유무 무관), 5 = `--exit-code-violations`이고 위반(warning 포함) 있음, 3 = 입력 로드 실패(리포트 없음), 1 = 잘못된 플래그/값, 2 = spice netlist에서 모델 라이브러리 없음(파일은 써짐 — 실측 사실일 뿐, `KicadCli._run`은 0/5 외의 종료 코드를 모두 실패로 취급하므로 그 파일을 쓰는 코드 경로는 없다).
- ERC 위반은 `sheets[].violations[]`, DRC는 `violations` / `unconnected_items`(severity error) / `schematic_parity` 세 리스트. 항목의 `type`·`severity`·`excluded`만 안정적이며 `description`과 stdout/stderr는 모두 로컬라이즈(한국어)된다 — 텍스트 매칭 금지. `--severity-all`은 사람이 제외한 위반도 `excluded: true`로 포함하며 우리는 그것도 error로 센다.
- `--schematic-parity`는 `<stem>.kicad_sch`가 보드 옆에 있어야 한다. 없으면 exit 0, stderr에 메시지, `schematic_parity: []` — 즉 조용히 "통과". `run_drc`는 sibling 부재를 `ToolExecutionError`로, 실행 후 비어있지 않은 stderr도 오류로 취급한다(성공 실행의 stderr는 항상 비어 있었다).
- ERC JSON의 `pos`는 실제 값의 1/100 (KiCad 버그, DRC는 정상). 위치를 쓸 일이 생기면 ×100.
- Gerber: 기본은 Protel 확장자(.gtl/.gbl/.gts/.gbs/.gm1 …), `--no-protel-ext`면 전부 `.gbr`. `<stem>-job.gbrjob`는 그 실행이 쓴 파일을 정확히 나열하므로 `export_gerbers`는 manifest로 결과 목록을 만든다. 헤더 `%TF.FileFunction`은 `Copper,L1,Top` / `Soldermask,Top` / `Profile,NP`, manifest는 `SolderMask,Top` / `Profile` 로 철자가 다르다. drill export는 구멍이 없는 보드에도 `<stem>.drl`(M48…M30)을 쓴다.
- 모든 export(gerber/drill/gbrjob/pos/netlist)에는 타임스탬프가 들어가므로 바이트 동일성은 우리가 컴파일한 `.kicad_sch`/`.kicad_pcb`에만 요구한다. artifact 해시는 "어떤 파일을 검사했는가"의 증거다.
- `pcb export pos`는 기본 단위가 inch, PosY는 보드 좌표의 부호 반전, `--smd-only`는 THT(핀 헤더) 제외 — CPL 대조에 쓸 때 주의(현재 리뷰어는 `pos` 대신 `.kicad_pcb`의 `(footprint (at ..) (layer ..))`를 직접 읽는다).
- `pcb drc --refill-zones`와 `pcb export gerbers --check-zones`는 stderr를 비운 채(parity 병행 시에도) 존을 메모리에서 채운다; 없으면 DRC는 존 동박을 못 보고(존만으로 이어진 GND는 `unconnected_items`) gerber에는 G36 영역이 전혀 없다.
- 하면 풋프린트의 `PAD::Flip(TOP_BOTTOM)`: `(chamfer top_left top_right)`는 `bottom_*`로, `(rect_delta x y)`는 y 반전, custom `primitives`는 y 반전, 나머지 스칼라 유지 — 각각 `lib_footprint_mismatch` warning 유무로 실측(L_Bourns_SDR0604, Analog_QFN-28-36-2EP, AMS_LGA-10-1EP, BatteryHolder_Keystone_1057).
- KiCad 리포트 severity는 `error`/`warning`; `--severity-all`로 exclusion도 포함된다. ERC 컨테이너는 `sheets[].violations`, 이 키가 없으면 우리는 오류로 취급한다.
- `%LOCALAPPDATA%\Programs\KiCad\<ver>`의 `<ver>`는 문자열 정렬로 `9.0 > 10.0`이 되므로 숫자 튜플로 정렬한다(`cli.version_key`).
